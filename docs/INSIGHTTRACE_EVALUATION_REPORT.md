# InsightTrace 项目评估优化报告

评估日期：2026-09-18  
评估范围：附件驱动的经营分析、模型报告生成、审校、实时反馈和回归测试。

## 1. 结论先行

本轮没有推翻现有架构，而是围绕最影响正确性和可用性的链路做了小步优化。
优化后，确定性计算仍然负责指标和证据，大模型只负责组织语言；真实工作簿回归中，
模型输出通过了数值与因果边界审校，不再触发安全回退。

当前项目可用于本地演示和继续开发，但还不是无人值守的生产级系统。它已经具备
“可计算、可审校、可回归、可解释”的基础闭环。

## 2. 系统是怎样工作的

```text
用户问题 + 附件
      │
      ▼
FastAPI 创建任务 ──► PostgreSQL 保存任务、消息和附件
      │
      ▼
任务执行器读取附件
      │
      ├─► 确定性分析：清洗行、计算漏斗、Shapley 分解、生成证据
      │
      └─► 大模型：只根据可信指标和证据撰写管理摘要
                         │
                         ▼
                    报告审校器
                  ┌──────┴──────┐
                  │通过          │不通过
                  ▼              ▼
              使用模型摘要    回退确定性结论
                  └──────┬──────┘
                         ▼
                保存结果并实时推送前端
```

更适合初学者阅读的完整架构说明见
[小白版架构图](../ARCHITECTURE_FOR_BEGINNERS.md)。

## 4. 发现的问题、根因和修改

### 4.1 模型重复读取整份行数据

- 现象：确定性工具已经算完指标，模型仍收到十几万字符原始行，容易重新计算、添加
  未进入可信证据的数字，导致审校拒绝。
- 根因：同一份数据同时交给“计算层”和“表达层”，职责边界不清。
- 修改：确定性附件分析成功后，仅向模型保留附件元数据，并传入可信指标与证据；
  无法确定性识别的数据仍保留受控摘录，避免能力退化。
- 结果：同一上下文由 150,009 字符降至 14,856 字符，减少约 90.1%。

### 4.2 当期消失的维度被漏算

- 现象：某商品上期有订单、当期完全消失时，贡献率分母只统计当期仍存在的维度。
- 根因：总变化量从“当期键集合”计算，而不是两期维度并集。
- 修改：先取两期维度并集，再逐项计算 `当期 - 上期`。
- 回归：商品 B 从 10 单降到 0 单的案例现在正确显示为 100% 同向贡献。

### 4.3 脏行可能污染比率口径

- 现象：同一行点击量无效但下单量有效时，分子和分母可能使用不同样本。
- 根因：各字段独立求和，只跳过单个无效单元格。
- 修改：核心漏斗字段有任一无效时，整行退出核心指标和维度计算；报告明确披露
  无效行数和处理方式。

### 4.4 审校器会误伤否定句

- 现象：“不能认为完全由……”也会因为包含“完全由”被判成过度因果。
- 根因：只做简单子串匹配，没有识别同一分句中的否定词。
- 修改：增加分句级否定识别，同时保留对真正强因果表述的拦截。

### 4.5 用户看不到报告是否通过审校

- 现象：后端记录了审校事件，但 WebSocket 和前端执行过程没有展示。
- 修改：实时事件增加 `report_audit`，明确显示“审校通过”或“已安全回退”；任务日志
  同时记录是否接受模型输出、审校发现、上下文字符数和是否省略原始行。

### 4.6 缺少稳定质量基准

- 修改：新增数据驱动 Golden Set 和命令行评估器，覆盖中文字段、英文字段别名、
  指定月份、维度消失、脏数据披露、事实层级和关键证据。
- 原则：测试数据与评估逻辑分离，可继续向 JSON 文件追加真实坏案例。

## 6. 如何重复评估

在项目根目录运行：

```powershell
docker compose --profile test build backend-test
docker compose --profile test run --rm backend-test python -m evals.run_golden
docker compose --profile test run --rm backend-test ruff check app tests evals
docker compose --profile test run --rm backend-test

cd frontend
npm test -- --run
npm run build
```

Golden Set 位于 `backend/evals/golden_attachment_cases.json`。以后发现模型或计算坏案例时，
先把最小复现数据加入这里，再修代码，能够避免旧问题反复出现。

## 7. 尚未完全解决的风险

1. 当前任务执行器是单进程数据库轮询，适合本地和小规模演示，不适合高并发生产环境。
2. 附件解析仍发生在 API 进程，大文件虽然有限额，但生产环境应拆到独立任务队列。
3. Golden Set 目前只有 4 类合成案例，后续应持续加入真实匿名坏案例，并单独统计
   数值正确率、证据完整率、因果越界率和模型审校通过率。
4. 当前审校器以规则为主，能兜底常见数字漂移和强因果措辞，但不能替代完整的语义
   事实核验。
5. WebSocket 采用数据库轮询，部署多个实例后应增加消息总线或事件通知机制。

## 8. 依赖与兼容性

本轮没有引入新框架、数据库、SDK 或第三方依赖；沿用 FastAPI、SQLAlchemy、
PostgreSQL、React、TypeScript、Vitest 和现有 OpenAI 兼容模型接口。
